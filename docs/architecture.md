# Architecture

```
browser (apps/web)  ──/api──▶  Fastify (apps/server)  ──▶  Meta Responses API (Spark, SAM)
                                   │                   ├─▶  Home Assistant REST API (switching)
                                   │                   └─▶  MQTT broker ─▶ Home Assistant (our entities)
                                   └─▶  SQLite + files in .data/
```

The browser never talks to Meta or Home Assistant directly. Keys and tokens live in the server's `.env`, except a Home Assistant token made by signing in from the lab, which is kept in `settings` (`.data/`, on this machine) and never sent to the browser.

## Modes

Every request carries a `mode`, either `demo` or `live`.

- **demo** is the office seen by a camera mounted in its front corner: the isometric office rendered through `DEMO_CAMERA` (`packages/domain/src/demo-room.ts`), hand-written discovery results, synthetic SAM masks read off that render, and a virtual lamp. It never makes network calls. The mug can stand at one of three `DEMO_POSITIONS` on the desk, in room tiles: the frame is rendered with it there, its mask is the render's own pixels, and each position counts as its own source image.
- **live** validates and re-encodes an uploaded image with `sharp`, then calls the real services. Each outbound Meta attempt is counted against a per-day limit in SQLite _before_ the request is sent, so failures count too.

Demo and live have separate desk memory. Demo runs never count toward the live checklist in the UI.

## Server

`buildApp` (`app.ts`) creates the shared pieces once (the store, the Meta adapter, `run`, the jobs, the desk service, switching) and registers one Fastify plugin per resource under its URL prefix: `/api/desk`, `/api/fixtures`, `/api/scene`, `/api/item`, `/api/room`, `/api/jobs`, `/api/cameras`, `/api/streams` and so on. Each plugin takes what it needs from `RouteDeps` (`route-deps.ts`). `tests/routes.test.ts` pins every method and path, so a route that moves or disappears fails a test.

Route request bodies are zod schemas in `packages/domain/src/requests.ts`, shared with the web, which types its calls through the route table in `routes.ts`. Errors go through `LabError`: anything else is logged with its stack and answered as `internal`, and only SDK and network failures count as `upstream_failure`.

## Web

- **State.** `LabProvider` (`workspace/useLabState.ts`) composes one hook per slice under `workspace/state/` (view, desk, camera, fixtures, calibration, AI tasks, the run log and so on), each with its own interface and context. A pane reads only the slices it uses (`useLabParts(useView(), …)`), and `useStableSlice` keeps a slice's identity until a value in it changes, so a pane renders for changes it can see. Fast-changing values (the 10 Hz follow box, an AI task's progress) live in small stores outside React (`state/store.ts`) that only their readers subscribe to. A clock a pane shows is its own `useNow()`.
- **Calls.** `api()` (`api.ts`) types each call from the domain's route table, with a `method` option, `apiAt` for paths built at run time and `apiBlob` for files. A job's progress comes over its event stream (`state/follow-job.ts`), polling only if that fails.
- **Sprites** are drawn in a Worker (`iso/sprite.worker.ts`) and served as object URLs from a least-recently-used cache (`iso/sprites.ts`); `useItemSprite` and its siblings keep the last image until the new one is ready.
- **Chunks.** The editors, dialogs and the Playground load on first use (`React.lazy`); React has its own chunk, and the domain package is marked free of side effects so unused modules drop out.

## Domain package

`packages/domain` is pure TypeScript shared by the server, the web, the scripts and the tests. `index.ts` only re-exports. Beside the models and algorithms it holds the wire types (`api.ts`), prices (`cost.ts`), desk memory and its schema (`memory.ts`), zone rules (`rules.ts`), route request schemas (`requests.ts`), the web's route table (`routes.ts`), run outputs typed by kind (`run-outputs.ts`), shared numeric helpers (`math.ts`) and the room bench's cases (`room-cases.ts`). The kernel's hot loops (`voxelize`, `renderSprite`, `renderRoom`, `refineFit`) avoid allocating per voxel or pixel; a change there must leave the goldens and the benches as they were.

## Placement rule

`placementGate` in `packages/domain` makes the decision. A placement is **inside** only when:

- an observation exists for the remembered object and is less than five minutes old,
- a zone was saved on the same source image (zones are tied to a SHA-256 of the prepared image, not to physical coordinates), or the camera is marked fixed and the zone was drawn on a frame of the same size, and
- the whole detection box fits within the zone.

**Fixed camera.** Off by default. When a person marks the camera as fixed, `zoneApplies` lets a zone carry over to any new frame of the same size, and every decision made that way records `assumedFixedCamera: true`. A calibrated room camera ([below](#the-room-camera)) replaces the assumption: a zone drawn in the room (`onSurface`) applies to every frame that camera sends, records no assumption, and the watcher checks that the camera stayed put.

**Lamp on entering.** Desk memory keeps the last inside/outside verdict, and each decision records a `transition`: `entered`, `stayed_inside`, `left` or `stayed_outside`. The lamp fires only on `entered`. Saving a new zone or resetting clears the verdict, so the next inside counts as entering. Blocked decisions don't change it.

A newer segmentation replaces the current observation. Each segmentation can still trigger the lamp at most once: `claimPlacement` writes a row before the lamp call, and the pending event is saved first. If the process dies mid-call, the record stays `unconfirmed` and is never retried automatically.

## Tracking

The first identity is always manual: a person confirms a mug mask with `desk/select`. After that, `desk/track` takes the newest mug segmentation, picks the detection that overlaps the last box most (or the nearest one when none overlap) with `pickTracked`, records it as a `tracked` observation with its overlap, and verifies it in the same request. With look-alikes followed beside it (things of the same concept), `pickTracked` assigns the detections to all of them at once (`assignTracks`, `packages/domain/src/assign.ts`: the Hungarian algorithm on overlap and distance), so a thing never takes its neighbour's, and refuses with `track_lost` when the others account for every detection; its `margin` says how much better that assignment is than the other way round. A frame with no mug changes nothing. Earlier observations are kept, newest first, in the memory's `history` (up to 12), which the lab shows as a timeline and a trail on the scene.

**Local first ([plan](plans/multi-tracking.md#local-first)).** Tracking makes no AI call unless someone turns it on: _Let tracking call AI_ in the lab's settings (`POST /api/settings/tracking-ai`, kept in `settings` as `tracking_ai`, off when absent; `status.tracking.ai`). While it is off:

- **Outlines** come from a box (or polygon) a person drags around the thing: `POST /api/segment` with a `shape` outlines it on the server (`outlineIn`, `packages/domain/src/outline.ts`). What surrounds the shape is sampled from a band outside it and the shape's own edge and grouped into five colours (k-means); a pixel inside that is far from all of them is the thing; the largest piece, and any at least 30% of it, is kept and its holes filled. When under 6% of the shape stands out, the shape itself is the outline. It is recorded as an ordinary segmentation run (`model: 'local-outline'`, one detection, `local-outline.json` beside the source), so `desk/select`, `desk/objects/select` and `fixtures/anchor` take it as they take SAM's. On the demo render a box a few pixels around the mug, the book or the bottle outlines it at IoU 0.91–1.00 against the render's own mask; the render is flat-shaded, so a real photo will do worse. A shape always outlines locally, whether AI is on or not.
- **SAM by name** (`/api/segment` without a shape), **Spark's suggestions** (`/api/discover`) and **SAM finding a fixture** (`/api/fixtures/find`) refuse with 409 `tracking_ai_off`, in both modes, so the demo shows what live does.
- **The watcher** finds a lost thing by appearance, then over the whole frame by appearance in place of SAM, and marks it missing when that fails too; it never asks SAM for a person in a zone (`samConfirm`). Everything else it does is local already.

Tests build the app with it on (`testApp`'s `trackingAi`, on unless a test says otherwise), since most of them drive the demo's SAM stand-ins; `tests/local-first.test.ts` runs with it off.

**Following locally.** Calling SAM for every frame pays for detection when only matching is needed. `Follow locally` in the workspace cuts a grayscale template of the mug from the last SAM-confirmed frame and searches each new frame near the last box by normalized cross-correlation (`packages/domain/src/tracker.ts`). Nothing leaves the browser. The live camera is sampled every 100 ms at 160 px wide; in demo mode each mug move is one step.

- **Masked template.** Only pixels inside SAM's mask are matched, not the whole box, so the desk around the mug isn't part of what's being looked for. When the mug moves onto a different surface, such as a white shirt, the old background can't drag the match down. A mask too plain to match on its own (a white mug with no shading) falls back to the whole box.
- **Look-alikes.** Each match records its lead over the best match elsewhere in the search area. A lead under 0.1 means two places look like the mug, so the box holds still rather than jumping to the look-alike. A small distance penalty breaks ties in favour of where the mug was.
- **Lost.** A score under 0.6 or a lead under 0.1 counts as unsure. While unsure, the box holds still and the search widens each step, so a mug that moved fast can still be found.

- **Stillness.** Picking the mug up always breaks the match for a moment: a hand covers it, it tilts, it blurs. So neither kind of SAM call below goes out until the area around the mug (the box grown by its own size on each side) has been still for 8 samples, about 0.8 s. "Still" means under 1.5% of pixels changed by more than 24 grey levels, the same rule as the playground's motion gate. Once the mug is set down, the widened search usually finds it again with no SAM call at all. Motion elsewhere in view, like typing, doesn't count.

SAM runs again through the normal `desk/track` path only when:

- **confirm**: the local box sits on the other side of the zone edge for a few samples. Leaving is confirmed too, so the server's last verdict stays right and the next entry still fires the lamp. Live checks wait at least 2 s after the last one.
- **re-anchor**: the match stays unsure for a few samples. Live re-anchors back off from 2 s to 30 s while the mug stays lost, and reset after about 3 s of good matches. If SAM can't see the mug either, following stays on and tries again later.

In the browser's `Follow locally`, the lamp only ever fires on a SAM observation: the local box is a reason to look again, never a verdict. The server's watcher (below) judges zones where it follows a thing instead. The template is only cut from SAM frames, so it doesn't drift. The zone can only be watched when it carries over, meaning the camera is marked fixed. A white mug against a white shirt has almost no contrast to match on, so expect a re-anchor there rather than a confident local box. Big changes in rotation, scale or lighting also show up as weak matches and fall back to SAM.

**Watching on the server ([plan](plans/tracking.md)).** `Watch on the server` moves the following above out of the tab: rules fire with no tab open, and the browser's `Follow locally` is offered only for cameras the server can't read (this device's, a phone, a WHEP-only stream). `apps/server/src/watcher.ts` runs one `Watcher` per mode. It follows everything confirmed (`watchedThings`: the mug, other objects, tracked fixtures), each from the photo it was last confirmed in, since the camera is fixed. Each frame goes through `watchStep` (`packages/domain/src/watch.ts`): a thing whose region didn't change keeps its box after a motion check (microseconds), with a full match once a second in case it crept, and a lost thing isn't searched for again in a frame that hasn't changed; a changed one is matched by `stepLocalTrack`, its search started where its velocity puts it (an alpha–beta filter, the steady state of a constant-velocity Kalman filter, reset when it is still), so a thing being carried is looked for ahead of its last box; a crossing of any of its zones (the main zone and its rules, `zonesOf`) that has settled is judged where the local match has it (`placeLocally` in `desk.ts`): a copy of its sighting at the followed box goes through the same gates and switching as a SAM check (claimed as `local:<id>`), with no SAM call, and its remembered sighting stays SAM's, so the room draws it where SAM last saw it; a blocked judgement (a moved camera, no zone for the frame) waits 30 s before the next; a thing lost for a few frames is first looked for by appearance (every thing lost by then in one embedding of the region holding them, followed things' boxes left out, lost look-alikes scored as each other's rivals) and only then re-anchored, backing off from 2 s to 30 s: with tracking AI on, by SAM, one call per concept for every thing of it that needs one, on one snapshot, through the lab's own segment path (billed and recorded like the button), each answer going through `trackMug`, `trackObject` or `trackFixture`, which the routes use too; with it off, by appearance over the whole frame at 896 px. Three re-anchors that find nothing mark it `missing`: it is left alone until its old region moves, except that once every 10 s, when the view has changed, its template is matched over the whole frame, so a thing put back somewhere else is found with no model call.

- **Look-alikes.** Every thing is stepped together (`watchFrame`), each one's search skipping the others' boxes, so two look-alikes side by side aren't each other's runner-up and a lost one can't settle on one already followed. Two of one concept that come within a box width of each other while one moves are `entangled`: both are followed, but neither's zones are judged. Once they are apart and still, each one's template is scored at both places and they are assigned jointly; with a margin of `MULTI.minMargin` (0.15) they are sure again, swapped if their looks say so, else they stay entangled until a person confirms one. A SAM answer whose assignment has a smaller margin entangles the thing with its nearest look-alike too. Two identical mugs swapped by hand stay entangled: nothing on a fixed camera can tell them apart. Every successful desk, fixture, scene or item change syncs the watcher (`sync`), so things confirmed or zones drawn while it runs are followed at once. A spending limit or live calls being off pause SAM: following and local zone judgements go on, and a lost thing waits until SAM can be asked. `GET /api/watch/:mode/events` streams its state to the lab (state, each thing's box, which layer placed it, counts); `POST /api/watch` turns it on or off. Whether it's on, and which camera, is kept in desk memory as `watch`, which reset keeps, and it resumes when the server starts.

- **Frames.** `apps/server/src/frames.ts`. Live, an `FfmpegSource` reads the camera's RTSP URL (from mDNS, as `scripts/share-camera.sh` advertises it, an `rtsp://` entry in `CAMERA_STREAMS`, or a saved camera's stream URL; `POST /api/watch` only ever takes a stream id, never a URL) as raw grey frames, 320 px wide at 10 a second, from one ffmpeg process that decodes in hardware where it can (`-hwaccel auto`). The same process writes a full-size JPEG to a temporary file twice a second, so a picture for SAM or the feature model is a file read (about 30 ms) rather than a second, short ffmpeg run (about 2 s over RTSP, still the fallback); a file, not a second pipe, since two pipes hang under Bun. Every ffmpeg is ended with SIGKILL: on a polite signal it can wait on the camera and outlive the server. Watching is on by default: when the server starts, the live desk watches the camera it watched before, or else the one saved camera the server can read; a desk that never chose watches a camera as soon as it is saved. Pausing it lasts until the next start. A saved camera or the phone can keep a zoomed view (`crop`, shares of its whole frame, `POST /api/streams/crop`), kept on the server so every connection opens on it: ffmpeg cuts a saved camera's grey frames, stills and preview to it, and the tab cuts any WebRTC picture, the phone's or a relayed saved camera's (`cropStream`, on each decoded frame), so everything after sees the crop as the whole frame. The phone's is one setting, since each pairing is a new stream id. Calibrating through a crop fits the whole lens, its principal point at the full frame's centre, and keeps the crop's part of it (`cameraFromMarks` with `crop`), so a tight zoom still fits; a new view needs a new calibration. In demo mode a `DemoSource` renders the office through the demo camera with the mug at its position; each move under the canvas sends a few frames of it (`POST /api/watch/demo`), with no settling or waiting between checks.
- **Appearance (layer 2).** `apps/server/src/appearance.ts` runs DINOv3 ViT-S/16 (int8, via ONNX Runtime on the CPU: about 12 ms at 224 px and 45 ms at 448 px on an M-series Mac; CoreML was slower). `bun run fetch-model` downloads it into `DATA_DIR` with checksums; without it this layer is skipped. Each SAM sighting adds a prototype, the mean of the patch features under its mask (`prototypeOf`, up to four per thing). A lost thing's picture is embedded and the window of its size most like a prototype is where it is (`findByAppearance`), trusted only with a mean similarity of 0.6 and a lead of 0.06 over anywhere else (`appearanceSure`). On the old close-up illustrated desk a moved mug scored 0.83 to 0.87 and led by 0.15. In the demo room, where the mug is 17 × 23 pixels, a moved mug scores about 0.80 and leads by 0.03 or less, so it is never trusted and SAM is asked (see [the room camera](#the-room-camera)). A confident match moves the box there and following goes on with the template from SAM's frame; it is a reason to look again, never a verdict.
- **Stream cameras.** `Cameras` in the workspace's live capture bar adds a camera by its stream URL (`rtsp://`, `rtsps://`, or an `http(s)://` stream ffmpeg can open, such as MJPEG or HLS), with a name and optionally the room it looks at: a preset or the person's own scene (`packages/domain/src/camera.ts`, `apps/server/src/cameras.ts`). They are kept in `settings` under `cameras`, not desk memory, so they serve both modes and survive reset; at most 16. A URL can carry a user and password: the server keeps it whole and the page only ever sees it with the password as `***` (`cameraView`), so a change sent without a URL keeps the stored one. `/api/streams` lists each as `cam:<id>` with `source: 'saved'`, its room and a `snapshot` path. A tab can't play RTSP. With mediamtx installed, the server runs it as a relay for saved RTSP cameras (`apps/server/src/relay.ts`, `CAMERA_RELAY`, loopback ports from `CAMERA_RELAY_PORT`): it reads each camera once, on demand, and the stream lists it with `whep: /api/cameras/:id/whep`, which the lab forwards to the relay, so a tab plays it as WebRTC at the camera's own rate with ~100 ms latency. The watcher, stills and preview read the relay's RTSP too, so the camera has one client. The relay starts only once the server holds its port, and replaces one an earlier server left running (`.data/relay/mediamtx.pid`); its config, which holds the camera URLs, is readable only by its owner. Without the relay, or when WebRTC fails, a tab plays the server's MJPEG preview (`GET /api/cameras/:id/stream`, ffmpeg at 10 fps); a camera with neither gives one still (`GET /api/cameras/:id/snapshot`, one short ffmpeg run), opened like an upload. Watching one keeps `cam:<id>` and the redacted URL in desk memory; the watcher asks the registry for the real URL each time it starts (`cameraUrl`). Removing a camera that is being watched turns watching off. When the lab switches to a room with a camera assigned to it (or to the room it's a close view of: the office for its desk), that camera becomes the chosen source, unless the chosen one is assigned there too. Only the lab, on a loopback origin, can add a URL; the scheme check keeps ffmpeg off local files.
- **Fixtures.** A fixture is confirmed in the camera by hand, like an object: `POST /api/fixtures/find` points SAM at where it should stand (`fixtureInFrame`: where the camera last saw it, else its box drawn through the pin's camera; one box prompt, grown by half its size; the demo picks the render's outlines there), and `POST /api/fixtures/anchor` confirms one outline. It then carries `track` (its concept, sighting and history, and `seen`, `moved` or `missing`). Each new sighting sets `seen` and moves it, and its linked copies, through the pin with `placeSeen`, the same as a scan. It can be a rule's subject (`objectById` finds tracked fixtures), though not of a rule that switches itself. Moving it by hand, `POST /api/fixtures/untrack` or deleting it stops the following; rules it decided go with it. The room draws a missing fixture faded where it was last seen.

## The room camera

([plan](plans/corner-camera.md)) Each room has one fixed camera, mounted high in its front corner and looking across at the far corner, the way the iso view looks. The isometric room is the base for everything: the camera says what is in the room and where, and the room is drawn from templates. Nothing from the photo is pasted onto it.

- **The camera.** `RoomCamera` (`packages/domain/src/room-camera.ts`) is a pinhole camera in the scene's own tiles: x along the back wall, y along the left wall, z up, walls included. `projectRoom` and `unprojectRoom` go between the room and the frame.
- **Calibrating.** `POST /api/room/floor` has SAM outline the floor and the walls (two calls, live; the demo reads them off its render). `marksFromWalls` keeps the floor pixels with wall just above them, and fits each wall's floor line to the points that remain (most points within two pixels wins). Furniture against a wall hides stretches of it, not all. The corner is where the lines meet. Nothing is saved: the marks open on the frame (`RoomCalibrate.tsx`) to drag into place, beside the room's size and, optionally, the camera's height. While dragging, the camera is fitted in the browser and the floor's tiles are drawn through it.
- **Fitting.** `POST /api/room/calibrate` fits the camera with `cameraFromMarks`, a Nelder–Mead search over lens, aim, roll and height for a camera in the room's front corner. The corner and the two lines leave the lens trading off against the tilt, so a typical lens, a level camera and a 2.4 m height are weak priors. A wall's far end, ticked when it is in view, or a known height pins it down. A fit off by more than about 1/60 of the frame's diagonal is refused. The calibration is kept in desk memory as `camera`, with the frame's edges (`cameraEdges`), and the camera is marked fixed. The room's desk or table, seen through it, becomes the pin (`pinOf`); reset keeps both.
- **Moved.** Every 10 s the watcher compares the frame's edges with the calibration frame's (`cameraMoved`: an 80-pixel-wide gradient thumbnail, correlated at offsets up to 3 pixels). People walking through change some edges but leave the room lined up; a camera knocked aside lines up better at another offset, or not at all. Once it has moved, `camera.moved` blocks every placement and rule decision until it is calibrated again.
- **Scanning.** `POST /api/scene/from-photo` lays the room out through the calibrated camera (`layoutRoom`, `packages/domain/src/room-scan.ts`). Nothing is fitted to its outline. Each thing is drawn at its template's size, or at Spark's estimate for things that come in many sizes (desks, tables, shelves, cabinets, rugs; shelves and cabinets at Spark's height too, so a tall bookcase gets more shelves), and turned square to the nearest wall; a chair faces the nearest desk or table, and what stands on a surface faces as the surface does. Where it stands comes from the mask's lowest pixel in each column, dropped onto the floor or the top it stands on: from the camera's corner these land on the footprint's near sides or behind them, never in front, so their furthest reach gives the near sides. A template's own drawing, read the same way, says how far in from its box those sides are (a desk's legs, a monitor's stand). A thing whose back nearly touches a wall goes flush against it. A desk, table, shelf or cabinet grows (to 1.6 times its template) to hold what stands on it: each thing's near side, less its own depth, says how far the top must reach when Spark guessed it short. Floor pieces that overlap are pulled apart (`apart`), each pair by its cheapest fix: a desk, table or shelf gives up its far side, which was only estimated, or the other moves. A near side the frame cuts off, or one whose points fall behind a wall (something hides its foot), is only a bound, so that piece moves towards the camera cheaply instead: a desk whose drawers leave the frame moves out from the shelf behind it rather than losing a third of its length. A desk's or table's top, seen from above, says how far back it reaches (`topFar`), and it isn't cut shorter or pushed further forward than that. The numbers it weighs all this with are `LAYOUT_TUNING` (`layout-tuning.ts`), and `layoutRoom`'s `trace` option records each thing's evidence and every overlap fix it weighed (`bun run draft <run> --why <thing>`, `--trace`). Things the catalogue doesn't draw are turned with the surface they stand on, or to the nearest wall on the floor. A wall's floor line is often hidden behind furniture, so its marks are a guess; before laying out, the draft checks them against what stands there (`refineWalls`, `packages/domain/src/wall-refine.ts`). Nothing stands behind a wall, so when three or more things whose size is known (not a desk, table, shelf or rug Spark sized, nor a chair) would stand behind one (but not more than 4 tiles behind: that one hangs on the wall, like a calendar), its marks are turned about the corner, half a degree at a time, until the middle of those things just touches it, the other wall's length kept and this one's found again (`turnWall`). The middle one, because an outline that doesn't reach down to where its thing stands (a screen above its stand) would turn the wall too far on its own. The draft keeps the turned camera, and saving the draft saves it as the room's calibration. A wall marked too far out the other way only leaves things standing in front of it, which nothing says is wrong, so it stays. The review lays the room out again on every edit the same way, so its pin follows from the camera. `bun run bench:room` scans known rooms (`ROOM_CASES`, which the tests scan too) through cameras calibrated from their marks, and reports position, turn and size against `ROOM_TARGETS`. To reproduce a draft's failure, build the room with `sceneOf` (each thing's corner where it lands once turned) and scan it with `scanCase`, which calibrates from the marks and returns the layout, each thing's box and the verdict; its `crop` zooms the camera so the frame's edge cuts things off.
- **Small things.** Across a room a mug is about 17 × 23 pixels. The demo models its mug from a close photo of it (`demoCloseUp`), as a person would, and the appearance layer embeds a square seven times a thing's size around it (`appearanceRegion`), searching twice as wide at the same scale. At that size the feature model often isn't sure where a moved mug went; it is only a reason to look again, and SAM is asked.

## Isometric view

`Iso` in the lab stage draws the same desk memory as a room: an office, a desk or a fridge. The scenes are hand-made presets in `packages/domain/src/iso-presets.ts`, built from props on a tile grid. One tile is 30 cm and every template has its real size: a desk top stands at 72 cm, a book is 16 × 23 cm, a monitor 61 cm wide. Nothing is generated: props and item models are drawn by a code-only voxel kernel (`packages/domain/src/iso-voxel.ts`) as pixel-art sprites, which `apps/web/src/iso` places in an SVG scene with the zones, trail and labels on top.

- **Pinning.** A pin is a surface's top (the desktop, a fridge shelf) as four corners on the camera's frames, clockwise from the back left. In the room it comes from the calibrated camera: calibrating pins the room's desk or table, and `POST /api/desk/auto-pin` places any surface of the room where that camera sees it (`pinOf`), with no call. With no calibration it refuses with 409 `not_calibrated`. A person can still click the four corners by hand, which a close view of a desk (a preset with its own camera) needs. Nothing is saved until `POST /api/desk/surface` keeps the corners in desk memory as `surface`, and `surfaceMap` turns them into a homography from frame pixels to that surface. A pin applies to any frame of its size. Reset keeps it.
- **Placing.** `projectBox` stands the observation on the surface at the bottom-centre of its box, where it touches the surface, sized from the box's bottom edge. The trail and the zone are mapped the same way. A zone dragged on the iso surface is turned back into a frame `ZoneRect` (the bounding box of its corners), so `placementGate` is unchanged. The iso view never makes a decision.
- **Guessing.** `Guess scene` (`POST /api/scene/classify`, run kind `scene`) asks Spark which preset fits a live photo and which of its optional props are visible. The answer is checked against `sceneGuessSchema`, so Spark can only pick from the presets and props that exist. It is billed and counted like `discover`. The demo always answers `desk`.

- **Model kernel.** Every part is a signed distance function; `voxelize` samples their union on a grid (32 voxels along an item's longest side in the room, 64 in the editor, 16 per tile for plain props, and up to 64 per tile for furniture models, finer the smaller they are) with a normal, a colour, a material and ambient occlusion per surface voxel. `renderSprite` casts one isometric ray per pixel and lights the hit with a fixed key light, four-step ramps with cooler shadows (`rampLab` in `color.ts`), ordered dithering, gloss and metal highlights, see-through glass, a darker outline where the model meets the background, a line where a nearer part overlaps, and a two-step contact shadow. A prop with a `form` is drawn as a furniture model (`packages/domain/src/iso-furniture.ts`): parts built from its box's size, such as a desk's legs and rails, a chair's five-star base, seat, back and arms, a bookcase's shelves full of books, a monitor's panel, neck and foot, and a keyboard's keys, turned by the prop's `turns`. The parts are one sprite, so they hide each other correctly. The photo fitter and the room camera's renderer see the same parts (`propSolids`), a chair's base as a disc. Props are snapped to a palette built from the room's tones; items keep their photo's colours. A tracked object's width is held near what its kind really measures (`believableWidth`: a mug is about 12 cm), since a camera's view of a small desk can make it look a hand wide. Prop faces stay in the SVG, invisible, so picking and dragging still follow the geometry. `renderView` draws the same grid from the photo's camera, for fitting.
- **Item models.** `Model` opens an editor for a detailed model of the remembered object: up to 12 parts in item space, where the footprint fills the unit square and the height can reach 6 units (`packages/domain/src/iso-item.ts`). Shapes are `lathe` (a side profile turned on an axis, with an optional open top, inner wall and liquid), `rbox`, `tube` (a Bézier), `extrude` and `blob`; the first shapes (`cylinder`, `box`, `cone`, `handle`, `lid`) are turned into the new ones when an item loads (`upgradeItem`, run by `isoItemSchema` and `upgradeMemory`). Parts carry a material and up to six paint layers (`band`, `stripes`, `dots`, `top`, and palette-indexed `decal`s at most 64 × 32). A part can be locked so a refit keeps it.
- **Fitting to the photo.** `POST /api/item/draft` (run kind `item`) cuts the sighting out of its stored photo with SAM's mask (`maskedCrop`; the demo rasterizes `desk.svg`), picks an archetype (`iso-archetypes.ts`: mug, cup, bottle, can, book, box, plant, lamp, device, generic) and runs `fitItem` (`item-fit.ts`). It clusters colours in OKLab and merges lit and shaded clusters of one material. It finds the axis from the narrowest rows and a handle from the rows that stick out on one side, and reads the camera's elevation from the surface pin's foreshortening or else from the rim's ellipse. It then corrects the side profile for the stacked-ellipse outline a lathe makes from above, finds bands down the front, and unwraps the visible half of the surface into a decal. Finally it renders the model from the camera and nudges its numbers by coordinate descent until the silhouette matches the mask (at most 48 renders). The result is stored with a fit record: archetype, numbers, IoU, ΔE, elevation, views, crop and assists. `sampled` makes no model call. `spark` adds Meta's models, each only able to help: Spark names the archetype and material (`itemClassSchema`); SAM segments parts inside the crop (a handle, the liquid), which the fitter uses instead of its own guesses; Spark then compares a render with the photo and suggests corrections clamped to ±20% (`applyCheck`), kept only if the silhouette still matches. A later sighting of the same object is fused into the shape (`fuseFits`). `POST /api/item/refit` fits again to the stored crop, keeping locked parts; `GET /api/item/crop` serves the crop for the editor's `Photo vs model` overlay. `POST /api/item/save` stores edits and scores them again against the crop. The model lives in desk memory as `item`, survives new sightings, and is cleared on reset with the object. Extra objects (below) get models the same way, by `objectId`. `bun scripts/fit-bench.ts` measures fit accuracy on synthetic crops, the demo and any real crops in `testdata/items/`.
- **Templates and custom scenes.** Every scene is built from the prop palette in `packages/domain/src/iso-templates.ts`: desks, tables, shelves, a fridge, lamps, books and so on. One placed template is a group. Its props and surfaces share the group id as a prefix (`lamp`, `lamp:stand`, surface `desk:top`), and it moves, turns and goes as one. The presets are made of these templates too. `Edit layout` (the room's inspector) starts from a preset, an empty floor or a Spark draft. You add templates (`addTemplate` finds the first spot where nothing overlaps), drag and turn groups, and remove them. Tabletop templates settle onto whatever surface ends up under them (`settleGroup`). Groups that cut into each other are flagged, since the depth sort assumes boxes don't intersect. Where that sort still draws the wrong thing in front, a group or a fixture can be given a draw `layer` (−9 to 9, like a z-index): `depthOrder` draws layer by layer from the lowest and sorts by depth only within one. The editor's ⤓ and ⤒ buttons (or `[` and `]`) set a selected group's (`withGroupLayer`), and a fixture's or built-in thing's panel has the same pair. `POST /api/scene/save` checks the scene against `isoSceneSchema` and keeps it in desk memory as `scene`, which reset keeps. It becomes the room in the outline, and its surfaces can be pinned like a preset's. Saving a scene that no longer has the pinned surface clears the pin.
- **Spark layouts.** `Draft with Spark` in the scene editor (`POST /api/scene/draft`, run kind `layout`) asks Spark only which templates stand where on a grid, checked against `sceneDraftSchema`. `buildScene` builds the geometry, puts floor things first, settles tabletop things onto their surfaces, and checks the result against `isoSceneSchema`. Nothing is saved until you save it. The demo answers with a fixed layout of the office desk.
- **A scene from the camera.** `Upload a frame` or `Use the current frame` in the scene editor (`POST /api/scene/from-photo`, run kind `photo`; `apps/server/src/photo.ts`) drafts the whole scene and its objects from one frame of the room's calibrated camera, in two billed calls, three with the check. Without a calibration, or for a frame of another size, it refuses with 409 `not_calibrated` before any call. Spark lists up to 16 things, each a template or an archetype with a role (`surface`, `furniture`, `object`), what it stands on, a loose box in thousandths, its real size in centimetres, its colour and its material (`photoInventorySchema`). It gives no tiles or turns. One SAM call takes every box as a prompt under its own id (`segmentBoxes`, `buildObjectPrompt`), so each mask comes back labelled, and is saved as an ordinary segment run that sightings can point at. `layoutRoom` places them through the camera (see [the room camera](#the-room-camera)), and the main desk or table's pin follows from it. Each thing no template draws, and each small thing that may be tracked, gets a model without being fitted (`draftModel`): a saved fixture of the same name, else its archetype's own model from the catalogue, else a cube, in its colour and at Spark's size. Its masked crop is kept (`crops`) so Spark can model it properly later. With the check, Spark sees the frame beside the drafted room rendered through the same camera (`renderRoom`) and names what's missing or extra (`photoCheckSchema`). Anything missing gets one more SAM call if today's spending limit has room, and is kept if it lands in the room. When the check itself fails (a timeout, an overloaded model), the draft goes on without it and says so. A draft whose worst-case cost today's spending limit can't cover is refused before any call. In review, the layout runs again in the browser on every change: a thing drawn as another template, or one removed. `POST /api/scene/from-photo/save` writes the scene, the pin, the ticked objects (the first becomes the main one) and their models in one go. A tracked thing comes out of the room, drawn from its sightings instead (`sceneForSave`). Untracked things no template draws become fixtures with their model and crop as reference (`fixturesForSave`); one already in the room by the same name moves there instead. A scan draws only furniture with templates (`SCAN_TEMPLATE_IDS`): what stands on a surface, a monitor, a keyboard, a book, a lamp, becomes a fixture with its crop, so it can be modelled as the real thing, moved, and a lamp tied to its light. Its draft model is a saved fixture of the same name, else a desk model by what Spark drew it as or its name (`deskModel`: a monitor, a keyboard or a laptop), else its archetype's; it is placed with the template's drawn inset where one draws it alike (a monitor's stand). A lamp on the floor or taller than 110 cm gets the floor lamp's model (`floorLampItem`). A built-in lamp left in a room from before can be turned into a desk or floor lamp fixture from its panel, keeping its light. `POST /api/fixtures/sculpt` models such a fixture with Spark from that crop, seen from where the room's camera is. The demo lists the office's desk, mug, book and bottle, with masks read off its render, and lays them out through the demo camera.
- **Setting a room up from the camera.** `Set up from the camera` in the scene editor, also its `Start from` default whenever there is a frame (`POST /api/scene/setup`, run kind `photo`), does calibration and the draft in one go, calibrated or not, and captures its frame from the live camera when one is streaming. Spark's inventory call also estimates the room (`setupInventorySchema`: the walls running right and left from the far corner, and the camera's height), so the setup makes no more Spark calls than a draft: Spark once, SAM three times (floor, walls, boxes), plus the check if asked. The marks are read off the floor and walls as `room/floor` does (`findFloorMarks`), and the camera is fitted both ways round, with and without Spark's height (`fitRoom`). The best fit decides which wall is the room's back, so the scene's direction, and is saved as `room/calibrate` saves it (`calibrateRoom`). It goes on by itself only when both walls' floor lines are seen: with one, a fit bends the camera to that line and passes while wrong. Reading the lines allows a skirting board's gap between the floor's mask and the wall's; when furniture hides one wall's line, `marksFromWalls` keeps the other and puts the corner where that wall's own mask ends along it. No floor, a hidden wall or marks that fit no corner camera stop the setup with 422 `calibrate_by_hand`, whose `data` carries the marks it found, Spark's sizes and the frame: the lab stops the camera on that frame and opens calibration with them (`calibrateByHand`), a hidden wall starting as a line to drag, so the person only sets the corner and that wall. Then the draft above runs through the new camera (`draftThrough`, shared with `scene/from-photo`), and its review shows Spark's estimate and the fit (`PhotoDraft.setup`). `↻ Rotate scene` turns the whole layout a quarter (`rotateScene`): its grid's sides swap and the back and left walls stay put. A calibrated camera then needs calibrating again, since it was fitted to the room the other way round.
- **More objects, zones and lights.** The outline adds up to four more objects and eight more zones (sighted fixtures and `rules` in desk memory: the mug and every other object are fixtures with `place: 'sightings'`, read with `mugOf` and `otherObjects`). An extra object is confirmed by hand from a mask in the newest segmentation, of any concept, and then tracked only in segmentations of that same concept (`desk/objects/select`, `desk/objects/track`). A rule ties a zone to what it counts and one entity (`entityId`, a light or a switch, optionally picked as a fixture by `fixtureId`). What it counts (`objects`) is `any` thing the camera follows (`followedIds`: the mug, other objects, tracked fixtures) or a list of them; a fixture never counts toward the entity it switches (`ruleObjects`). Rules saved with only `lightId`, or with one `objectId`, are upgraded on load by `upgradeMemory`. `ruleGate` checks each counted thing as `placementGate` checks the mug (a fresh sighting, a zone drawn on that image or carried over by the fixed-camera assumption, standing in it: `standsInZone`, the middle of its base on the pinned surface for a zone drawn in the room, else its box's bottom centre on the frame) and keeps which are inside (`inside`); a thing with no fresh verdict keeps its last place, so a stale sighting neither fills nor empties the zone, and the zone is blocked only when no counted thing has a verdict. The zone is occupied (`placement: inside`) while any counted thing is in it. Each rule keeps its own occupied/empty story, switches its entity on when it fills (`entered`) and, with `offWhenEmpty`, off when it empties (`left`), and claims `segmentRunId:ruleId` (`:left` for switching off) before the call, so one segmentation can try each at most once. Rules are checked when any thing they count is tracked (the mug's rules too, after the main zone) and on `Check rules`; forgetting a thing drops it from rules naming it, and a rule left counting nothing goes (`withoutThings`). The main zone is the rule `main` (`MAIN_RULE`, `entityId: ''` for the main lamp), read with `mainZone` and checked first; saved desks with the old `object`, `zone` and `others` are moved over by `upgradeMemory`. Live lights are `HA_ENTITY_ID` plus `HA_EXTRA_ENTITY_IDS`, live switches are `HA_SWITCH_ENTITY_IDS`, and the control adapter (`control.ts`) refuses any other entity. It calls `light/turn_on`, `light/turn_off`, `switch/turn_on` or `switch/turn_off` by the entity's prefix, turns a light on as its zone's look asks (`look`: its own colour, which Home Assistant restores, by default; warm white; or a colour, sent as `rgb_color` to a bulb with a colour mode and judged by `hs_color`), with `transition: 0`, and polls every 100 ms until the entity reports the requested state. What an entity can do is read once and kept for 10 minutes, so an action needs no read first; the watcher's own checks have the state confirmed in the background, recording the decision again once it is. Demo mode has three virtual lights and two virtual switches (`DEMO_SWITCHES`). Only a light turned on counts as live proof of the lamp. In a scene, a lamp prop stands for the main light unless the scene editor ties it to another (`lightId`). The demo's synthetic SAM only knows the mug, so in demo mode rules can only target the mug.

- **Flat things and lamps.** A `device` (a mouse, a remote, a switch plate) is its own shape family, `flat`: one `extrude` part whose outline is read off the mask in twelve directions from its middle, as a reference photo from above shows it, with its top colour and any print as a top decal. A photo from above can't show height, so it comes from `knownHeight` (a fixture's usual size) or a typical one. The fitter's camera looks from the iso corner, which would see a top-down photo turned 45°, so a flat model is scored by drawing its outline flat over the crop (`scoreFromAbove`) rather than by rendering. A `lamp` is a turned body (base, stem, shade); a shade keeps widening below its rim, so a lamp's camera angle is read from its base's bottom edge instead. Rim angles are read only from rows up to the widest point. Lamps still miss the 0.9 IoU target (about 0.85: the thin stem is lost between profile samples) and are listed as a known gap in the fit bench.
- **Fixtures ([plan](plans/fixtures.md)).** Things placed in a room by hand, which the camera can follow once confirmed in its view ([watching](#tracking)): a lamp, a wall switch, a mouse (`packages/domain/src/fixture.ts`). Each stands in one scene, on a surface or the floor, with a voxel model and a control: `none`, or a `light` or `switch` entity. They live in desk memory as `fixtures`, survive reset, and settle when the person's own scene changes (`settleFixtures`: a lost surface drops them to the floor; dropping the scene drops its fixtures). `POST /api/fixtures/save` checks where one stands (`fixtureProblem`) and that its entity is configured; `POST /api/fixtures/delete` unlinks rules that picked it; `POST /api/fixtures/control` turns its light or switch on or off as a `lamp` run. Any confirmed action on an entity, from a rule too, sets `state` on the fixtures that switch it (`noteControl`); an unconfirmed one clears it. `POST /api/fixtures/draft` (run kind `fixture`) drafts one from a reference picture: the thing's mask is cut out (`maskedCrop`) and modelled by `draftModel` in `item.ts`, the same part masks, fitter and Spark check that `POST /api/item/draft` uses, then sized for the scene it's meant for (`sizeInTiles`: a desk is 120 cm wide, else a tile is 25 cm). Nothing is saved; the draft (`FixtureDraft`) carries the model, a suggested control, the size and the reference photo. Saving a fixture whose reference is a draft keeps the draft's swatches and fit record, rescored against its crop. Live, the person's photo is checked and re-encoded (`validateImage`), Spark names the one thing in it (`fixtureClassSchema`: a label, an archetype, a material, a suggested control, a loose box in thousandths and its usual size in cm; an optional name from the person is passed along), and one SAM call outlines it from that box (`segmentBoxes`); the biggest outline wins, and none is a 422 that asks for one thing filling the frame. The crop then goes through `draftModel` with part masks and Spark's check. Up to five billed calls; a draft whose worst case today's spending limit can't cover is refused before any call, and the run is billed by its Spark tokens like `item`. Demo mode drafts only from the bundled `mouse.svg` and `lamp.svg`, whose masks are the SVGs' own `<name>-body` polygons. In the lab, fixtures have their own section in the outline. `Add fixture` opens photo first: the drop zone for a photo of the thing (`Take a photo` opens the camera on phones, `Upload` a file picker; the photo is scaled to 1280 px in the browser, and an optional name tells Spark what it is), and in demo mode the bundled pictures instead. The review shows the reference beside the model, then the name, `Light · Switch · Just a thing` (preselected from the suggestion, and only offering kinds with configured entities) and the room. `Place it` switches the canvas to that scene, where a ghost of the model follows the pointer onto the highest surface under it, or the floor, until a click saves it (`GET /api/fixtures/reference` serves the photo for review). A selected fixture can be switched on and off, moved the same way, turned, changed or deleted (`FixturePanel.tsx`). In the room a light that is on glows like a lamp; a switch shows its state in its label, never in amber. A fixture can also be drafted from a box drawn on the desk photo (live: Spark sees only the boxed part, SAM outlines it from the box; demo: the box picks one of the render's own outlines), and its model edited in the item editor like an object's. Lamps that are part of a room's layout are listed under Fixtures too and can be switched by their entity; every lamp glows by its light's newest confirmed state, from a switch, a rule or the mug's zone. A fixture's model can be improved afterwards, as [image-to-fixture.md](image-to-fixture.md) describes: `POST /api/fixtures/photo` fits another photo and fuses it with its fits (`fuseFits`, weighted by how much wider its crop is); `POST /api/fixtures/refine3d` (experimental) reshapes a turned body from a SAM 3D splat as a background job; each keeps the model it replaces in `drafts`, and `POST /api/fixtures/choose` puts one back, noting the pick in `fixture-picks.jsonl`. A draft matching a saved product takes its real size; a scanned thing is sized through the pin's camera (`cameraScale`). A fixture's `Type` (what it is among the starters, `fixtureType`) can be changed from its panel: `retypeFixture` gives it that starter's model in its own colours, at that kind's real size, centred where it stood, with that kind's states; the save keeps the old model in `drafts`. A model's parts named `shade` or `shade-…` are its light sources (`lightSources`: a floor lamp's uplight bowl and reading shade), and each can be linked to an entity of its own (`lights`, besides `control`). `POST /api/fixtures/control` with a `part` switches one source; `noteControl` keeps each source's confirmed state in `lit`, which lights only that shade (`fixtureModel`), and a source without an entity of its own follows the fixture's state. A rule may name the fixture by any entity it switches (`fixtureEntities`).

Amber stays reserved for lamps: an iso lamp warms only once an action on its light is confirmed.

## The AI brush

([plan](plans/ai-brush.md)) A person selects part of the camera's picture (a box or a polygon) and says what to do with it: _"It's an IKEA Alex desk, make it its own furniture"_, _"make the drawers green"_. The result is a draft to review; nothing changes in the room until it is put there.

- **Recipes.** A model as data (`packages/domain/src/recipe.ts`): named parts in real centimetres, each with a role (top, leg, drawer, panel…), drawn by `propModel` and seen by `propSolids` like any built-in form. Edits are a closed set of ops over part selectors (`recipe-ops.ts`).
- **Selections** (`selection.ts`, `POST /api/select/resolve`) are read through the calibrated camera: the room drawn labelled per pixel, each thing scored by how much of it the selection covers and how much of the selection it fills.
- **A request** (`POST /api/assist`, run kind `assist`, `apps/server/src/assist.ts`) holds the frame, finds what the selection is of through the room as the panel does, outlines it (SAM's box prompt cut to the shape, kept only when it is of the same thing, else the room's own drawing of it), reads the sentence into ops (Spark, `intent.ts`; the demo's own reader offline), looks up a named product (`research.ts`: saved products, the bundled catalog, Spark's web search, the camera's own box fit), builds the model from a form (`recipe-build.ts`), and checks it by drawing the room with it in place through the camera. Spark refines a new model at most twice; never one whose size the person gave. A refinement that fails keeps the model as built and says so. Follow-ups name the run before and cost one reading. The worst case, about $0.25, is refused up front against the day's limit.
- **Saving** (`POST /api/assist/save`) puts the model in the room as furniture in place of what was selected; a preset room becomes the person's own scene first (`adoptPreset`).
- **Offline:** `bun run assist <run>` replays a stored request with the current tree; `bun run bench:intent` reads sample requests.

## Home Assistant entities

([plan](plans/mqtt.md)) Rules act _on_ Home Assistant over REST. In the other direction, Living Layer publishes entities of its own over MQTT discovery, which appear in Home Assistant under one _Living Layer_ device, for automations and dashboards there. Nothing is published until someone adds one in the lab's outline (_Home Assistant_ section).

- **What one is.** `exposed` in desk memory (`packages/domain/src/expose.ts`): a name, a key, a kind (`binary_sensor` or `sensor`) and a source. The key `office_presence` gives `binary_sensor.ll_office_presence`; Home Assistant ids have one dot, so the `ll_` prefix stands for the namespace. Sources: `in_zone` (a zone's SAM verdict), `any_inside` (any of several zones; as a sensor, how many), `zone_of` (which of an object's zones it's in, an `enum` sensor), `status` (seen, searching or missing, from the watcher, else desk memory), `motion` (pixels changing in a zone, held for `holdS`; the watcher's stillness rule per zone, no SAM, needs the watcher on and the camera fixed) and `watching`. Zones are named by rule id, the main zone as `main`. Reset keeps entities; one whose zone or object is gone shows as unavailable, so automations notice.
- **Zones that only tell Home Assistant.** A rule's entity may be null (_nothing: tell Home Assistant only_). `ruleGate` decides it like any other, it keeps its inside/outside story, and it never claims or switches anything. A rule panel's _Also show in Home Assistant_ makes an `in_zone` entity for it.
- **States.** `evaluateExposed` is the only place states are worked out, from desk memory and the watcher's `exposeWatch()`. Zone sources read SAM verdicts only, like the lamp. While the watcher runs a verdict stands until SAM changes it; without it the last verdict stays, with `stale: true` among the attributes. A zone with no verdict yet is unavailable.
- **Publishing.** One `Exposer` per mode (`apps/server/src/expose.ts`) syncs after every successful POST to the desk, fixture, scene, item, watch and expose routes, on every watcher update, and every 5 s for motion holds. It diffs `exposeMessages` (configs first, all retained) against what it last sent, publishes the changes, and clears what went away; an entity that is only unavailable keeps its last state. Config topics are remembered in `settings`, so ones deleted while the server was down are cleared on the next sync. Each config carries `unique_id` (`livinglayer_<install id>_<entity id>`, the install id made once in `settings`), `default_entity_id` (not the removed `object_id`), and two availability topics, `<base>/status` (the broker's last will) and the entity's own. `MqttLink` resends everything on each connect and when Home Assistant publishes `online` on `<prefix>/status`. Live only: demo mode never touches the network and keeps a log of what it would have sent, which the entity panels show (_What it would publish_). The lab follows states through `GET /api/expose/:mode/events`. Broker credentials stay in `.env`; the lab sees the broker's state and a generic note.

- **Presence, locally.** An `occupied` source compares a zone with how it looked empty, which the person shows once (_It's empty now: learn it_, `POST /api/expose/learn-empty`), so someone sitting still still counts. With the feature model (`bun run fetch-model`) the zone's patches are compared (`featureDifference`: the share whose cosine with the empty look is under 0.8); without it, a 32 × 24 grey sample (`pixelDifference`), which light changes fool. Occupied from 12% changed, clear again under 6%, every 3 s while watching (every frame in the demo), from the watcher's grey frames, so no extra ffmpeg run (`packages/domain/src/occupancy.ts`). Empty looks are kept in `settings` per mode and zone. Nothing paid by default: `samConfirm`, a per-entity opt-in the form marks as billed, asks SAM for `person` once each time the zone starts to look occupied (at most once a minute), and the entity is on only if a person's box overlaps the zone. The thresholds are first guesses, not tuned on real rooms.
- **More kinds.** A `device_tracker` follows an object: its zone's name, `home` when it's in none, `not_home` when missing. An `event` entity (`event_types: entered, left`) gets each zone decision that entered or left once, not retained (`zoneEvent`; a new entity starts from what is already decided). A `switch` (`watching`) turns watching on and off with the camera last chosen in the lab (`setWatching`, shared with `POST /api/watch`); a `button` (`check_rules`) runs `verifyRules`. Commands arrive on `<base>/<key>/set` and `/press` and are taken only for our own switches and buttons, with their exact payloads (`commandOf`); the lab lists the last ten and what came of them. Live only.
- **Devices it may switch.** Rules and fixtures switch only devices on an allow list: `.env`'s `HA_*` entities, the `MQTT_DEVICES`, and the ones ticked in the lab's _Devices it can switch_ panel (`apps/server/src/ha.ts`, kept in `settings` as `ha_entities`). The panel lists Home Assistant's lights, switches, fans and toggle helpers from `GET /api/states` (`ControlAdapter.entities`, read only), and tries one through `POST /api/lamp` with an `entityId` and `action`. Only on and off: for more, a toggle helper (`input_boolean`) and an automation in Home Assistant. Connecting is a sign-in from the panel (`POST /api/ha/login`, `signIn`): Home Assistant's login flow with a username and password (and a two-factor code when it asks), the code traded for a short session, and that session asked over the websocket for a long-lived token named `Living Layer <time>`; the short session is then revoked. Only the origin, the token and the user name are kept (`settings`, `ha_login`), never the password; `POST /api/ha/logout` forgets them, and the token stays listed in Home Assistant until deleted there. `HA_URL` and `HA_TOKEN` in `.env`, when both are set, win over a sign-in. `HA_LIVE_ENABLED` is on unless `.env` sets it false.
- **Lights over MQTT.** `MQTT_DEVICES` names lights and switches by the topic they report on. They join the entities rules and fixtures may switch; with no `HA_ENTITY_ID`, the first such light is the main lamp. `MqttControl` publishes `{"state":"ON"}` (with brightness 217 of 254 for a light turned on) on `<topic>/set`, not retained, and waits up to 3 s for the device's JSON report with that state. Its `LampResult` reads the same as Home Assistant's: confirmed means the device reported it, not that light was seen. A retained report already in that state confirms at once.

## Lamp results

Home Assistant accepting a request, the entity reporting the requested state, and the bulb actually lighting up are three separate things. `LampResult` records the first two (`accepted`, `stateConfirmed`). `physicalEffectVerified` is always `false`, because the software has no way to see the lamp.

## Not built yet

- Telling identical look-alikes apart. SAM's answer is assigned by position (`pickTracked`, jointly with look-alikes), and two mugs that look the same to the template and the feature model stay `entangled` once carried past each other, until a person confirms one. A "Which one?" question in the lab is not built.
- Watching a phone camera on the server: a phone streams to the tab, peer to peer, and the server never sees its frames.
- Recalibrating by itself: a camera seen to move pauses its zones until a person calibrates it again.
- Combined conditions, such as two objects in their zones before one light turns on. A rule's zone is occupied by any one of the things it counts, never all of them, and switches one entity. Entities shown in Home Assistant let its automations combine them instead.
