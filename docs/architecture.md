# Architecture

```
browser (apps/web)  ──/api──▶  Fastify (apps/server)  ──▶  Meta Responses API (Spark, SAM)
                                   │                   ├─▶  Home Assistant REST API (switching)
                                   │                   └─▶  MQTT broker ─▶ Home Assistant (our entities)
                                   └─▶  SQLite + files in .data/
```

The browser never talks to Meta or Home Assistant directly. Keys and tokens live in the server's `.env`.

## Modes

Every request carries a `mode`, either `demo` or `live`.

- **demo** uses the illustrated desk in `apps/web/public/desk.svg`, hand-written discovery results, a synthetic SAM stream, and a virtual lamp. It never makes network calls. The mug can sit at one of three `DEMO_POSITIONS`: the web redraws the desk with the mug offset, the synthetic mask moves by the same amount, and each position counts as its own source image.
- **live** validates and re-encodes an uploaded image with `sharp`, then calls the real services. Each outbound Meta attempt is counted against a per-day limit in SQLite _before_ the request is sent, so failures count too.

Demo and live have separate desk memory. Demo runs never count toward the live checklist in the UI.

## Server

| File              | Responsibility                                                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app.ts`          | Routes for the individual probes (`text`, `discover`, `segment`, `lamp`), loopback host/origin checks, and recording each run as an evidence record |
| `desk.ts`         | The placement workflow: select a mug, track it, save a zone, mark the camera fixed, verify, reset                                                   |
| `meta.ts`         | Spark (structured JSON output) and SAM (streamed) through the OpenAI-compatible SDK, with retries disabled                                          |
| `sam.ts`          | Runs the SAM stream through `@meta-sam/parser` and rejects anything incomplete, mismatched, or oversized                                            |
| `lamp.ts`         | Turns one light on, then polls its state to see whether it matches                                                                                  |
| `store.ts`        | SQLite tables for evidence, desk memory, placement claims, the spend ledger and settings                                                            |
| `expose.ts`       | Entities shown in Home Assistant: works out their states, keeps the broker's retained topics in step, the lab's routes                              |
| `mqtt-control.ts` | Lights and switches switched over MQTT (`MQTT_DEVICES`): one command, then the device's own report                                                  |
| `mqtt.ts`         | One MQTT connection: last will, Home Assistant's birth message, retained publishes                                                                  |
| `errors.ts`       | `LabError`, and mapping upstream failures to generic messages so provider errors never leak keys or inputs                                          |

## Placement rule

`placementGate` in `packages/domain` makes the decision. A placement is **inside** only when:

- an observation exists for the remembered object and is less than five minutes old,
- a zone was saved on the same source image (zones are tied to a SHA-256 of the prepared image, not to physical coordinates), or the camera is marked fixed and the zone was drawn on a frame of the same size, and
- the whole detection box fits within the zone.

**Fixed camera.** Off by default. When a person marks the camera as fixed, `zoneApplies` lets a zone carry over to any new frame of the same size, and every decision made that way records `assumedFixedCamera: true`. Nothing checks that the camera really stayed put.

**Lamp on entering.** Desk memory keeps the last inside/outside verdict, and each decision records a `transition`: `entered`, `stayed_inside`, `left` or `stayed_outside`. The lamp fires only on `entered`. Saving a new zone or resetting clears the verdict, so the next inside counts as entering. Blocked decisions don't change it.

A newer segmentation replaces the current observation. Each segmentation can still trigger the lamp at most once: `claimPlacement` writes a row before the lamp call, and the pending event is saved first. If the process dies mid-call, the record stays `unconfirmed` and is never retried automatically.

## Tracking

The first identity is always manual: a person confirms a mug mask with `desk/select`. After that, `desk/track` takes the newest mug segmentation, picks the detection that overlaps the last box most (or the nearest one when none overlap) with `pickTracked`, records it as a `tracked` observation with its overlap, and verifies it in the same request. A frame with no mug changes nothing. Earlier observations are kept, newest first, in the memory's `history` (up to 12), which the lab shows as a timeline and a trail on the scene.

**Following locally (prototype).** Calling SAM for every frame pays for detection when only matching is needed. `Follow locally` in the lab cuts a grayscale template of the mug from the last SAM-confirmed frame and searches each new frame near the last box by normalized cross-correlation (`packages/domain/src/tracker.ts`). Nothing leaves the browser. The live camera is sampled every 100 ms at 160 px wide; in demo mode each mug move is one step.

- **Masked template.** Only pixels inside SAM's mask are matched, not the whole box, so the desk around the mug isn't part of what's being looked for. When the mug moves onto a different surface, such as a white shirt, the old background can't drag the match down. A mask too plain to match on its own (a white mug with no shading) falls back to the whole box.
- **Look-alikes.** Each match records its lead over the best match elsewhere in the search area. A lead under 0.1 means two places look like the mug, so the box holds still rather than jumping to the look-alike. A small distance penalty breaks ties in favour of where the mug was.
- **Lost.** A score under 0.6 or a lead under 0.1 counts as unsure. While unsure, the box holds still and the search widens each step, so a mug that moved fast can still be found.

- **Stillness.** Picking the mug up always breaks the match for a moment: a hand covers it, it tilts, it blurs. So neither kind of SAM call below goes out until the area around the mug (the box grown by its own size on each side) has been still for 8 samples, about 0.8 s. "Still" means under 1.5% of pixels changed by more than 24 grey levels, the same rule as the playground's motion gate. Once the mug is set down, the widened search usually finds it again with no SAM call at all. Motion elsewhere in view, like typing, doesn't count.

SAM runs again through the normal `desk/track` path only when:

- **confirm**: the local box sits on the other side of the zone edge for a few samples. Leaving is confirmed too, so the server's last verdict stays right and the next entry still fires the lamp. Live checks wait at least 2 s after the last one.
- **re-anchor**: the match stays unsure for a few samples. Live re-anchors back off from 2 s to 30 s while the mug stays lost, and reset after about 3 s of good matches. If SAM can't see the mug either, following stays on and tries again later.

The lamp only ever fires on a SAM observation. The local box is a reason to look again, never a verdict. The template is only cut from SAM frames, so it doesn't drift. The zone can only be watched when it carries over, meaning the camera is marked fixed. A white mug against a white shirt has almost no contrast to match on, so expect a re-anchor there rather than a confident local box. Big changes in rotation, scale or lighting also show up as weak matches and fall back to SAM.

**Watching on the server ([plan](plans/tracking.md)).** `Watch on the server` moves the following above out of the tab: rules fire with no tab open, and the browser's `Follow locally` is offered only for cameras the server can't read (this device's, a phone, a WHEP-only stream). `apps/server/src/watcher.ts` runs one `Watcher` per mode. It follows everything with a SAM sighting (`watchedThings`: the mug, other objects, tracked fixtures), each from the photo SAM last saw it in, since the camera is fixed. Each frame goes through `watchStep` (`packages/domain/src/watch.ts`): a thing whose region didn't change costs nothing; a changed one is matched by `stepLocalTrack`; a crossing of any of its zones (the main zone and its rules, `zonesOf`) that has settled asks SAM to `confirm`; a thing lost for a few frames is first looked for by appearance and only then asks SAM to `reanchor`, backing off from 2 s to 30 s. Three re-anchors that find nothing mark it `missing`, and it is left alone until its old region moves. SAM is asked one thing at a time through the lab's own segment path (billed and recorded like the button), and the answer goes through `trackMug`, `trackObject` or `trackFixture`, which the routes use too, so rules decide exactly as they do there. Every successful desk, fixture, scene or item change syncs the watcher (`sync`), so things confirmed or zones drawn while it runs are followed at once. A spending limit or live calls being off pause it: following goes on, and no rule can fire until SAM can be asked. `GET /api/watch/:mode/events` streams its state to the lab (state, each thing's box, which layer placed it, counts); `POST /api/watch` turns it on or off. Whether it's on, and which camera, is kept in desk memory as `watch`, which reset keeps, and it resumes when the server starts.

- **Frames.** `apps/server/src/frames.ts`. Live, an `FfmpegSource` reads the camera's RTSP URL (from mDNS, as `scripts/share-camera.sh` advertises it, or an `rtsp://` entry in `CAMERA_STREAMS`; never a URL from the page) as raw grey frames, 320 px wide at 10 a second, from one ffmpeg process. A full-size picture for SAM or the feature model is a second, short ffmpeg run (one process with two outputs hangs under Bun). In demo mode a `DemoSource` renders the illustrated desk at the mug's position; each move under the canvas sends a few frames of it (`POST /api/watch/demo`), with no settling or waiting between checks.
- **Appearance (layer 2).** `apps/server/src/appearance.ts` runs DINOv3 ViT-S/16 (int8, via ONNX Runtime on the CPU: about 12 ms at 224 px and 45 ms at 448 px on an M-series Mac; CoreML was slower). `bun run fetch-model` downloads it into `DATA_DIR` with checksums; without it this layer is skipped. Each SAM sighting adds a prototype, the mean of the patch features under its mask (`prototypeOf`, up to four per thing). A lost thing's picture is embedded and the window of its size most like a prototype is where it is (`findByAppearance`), trusted only with a mean similarity of 0.6 and a lead of 0.06 over anywhere else (`appearanceSure`). On the illustrated desk a moved mug scores 0.83 to 0.87 and leads by 0.15; a desk without it still scores 0.70 but leads by 0.03. A confident match moves the box there and following goes on with the template from SAM's frame; it is a reason to look again, never a verdict.
- **Fixtures.** A fixture is confirmed in the camera by hand, like an object: `POST /api/fixtures/find` points SAM at where it should stand (`fixtureInFrame`: where the camera last saw it, else its box drawn through the pin's camera; one box prompt, grown by half its size; the demo picks the illustrated desk's outlines there), and `POST /api/fixtures/anchor` confirms one outline. It then carries `track` (its concept, sighting and history, and `seen`, `moved` or `missing`). Each new sighting sets `seen` and moves it, and its linked copies, through the pin with `placeSeen`, the same as a scan. It can be a rule's subject (`objectById` finds tracked fixtures), though not of a rule that switches itself. Moving it by hand, `POST /api/fixtures/untrack` or deleting it stops the following; rules it decided go with it. The room draws a missing fixture faded where it was last seen.

## Isometric view

`Iso` in the lab stage draws the same desk memory as a room: an office, a desk or a fridge. The scenes are hand-made presets in `packages/domain/src/iso-presets.ts`, built from prisms and cylinders on a tile grid. Nothing is generated: props and item models are drawn by a code-only voxel kernel (`packages/domain/src/iso-voxel.ts`) as pixel-art sprites, which `apps/web/src/iso` places in an SVG scene with the zones, trail and labels on top.

- **Pinning.** A person clicks the four corners of one surface (the desktop, a fridge shelf) on a photo, clockwise from the back left. For a desk or table top, `POST /api/desk/auto-pin` finds them instead: SAM outlines `desk` (one call, saved as a segment run; the demo uses the illustrated desk's outline), and `pinFromMask` fits the biggest outline's top with the photo draft's surface fitter, then refines it against the template drawn from those corners. Nothing is saved: the corners open in the pin overlay to be dragged and saved, and a fit under 0.85 IoU asks for a check. `POST /api/desk/surface` saves them in desk memory as `surface`, and `surfaceMap` turns them into a homography from frame pixels to that surface. Like a carried zone, a pin applies to any frame of the same size and assumes the camera didn't move. The illustrated demo fills the frame with the desktop, so it uses `DEMO_SURFACE` without a pin. Reset keeps the pin.
- **Placing.** `projectBox` stands the observation on the surface at the bottom-centre of its box, where it touches the surface, sized from the box's bottom edge. The trail and the zone are mapped the same way. A zone dragged on the iso surface is turned back into a frame `ZoneRect` (the bounding box of its corners), so `placementGate` is unchanged. The iso view never makes a decision.
- **Guessing.** `Guess scene` (`POST /api/scene/classify`, run kind `scene`) asks Spark which preset fits a live photo and which of its optional props are visible. The answer is checked against `sceneGuessSchema`, so Spark can only pick from the presets and props that exist. It is billed and counted like `discover`. The demo always answers `desk`.

- **Model kernel.** Every part is a signed distance function; `voxelize` samples their union on a grid (32 voxels along an item's longest side in the room, 64 in the editor, 16 per tile for props) with a normal, a colour, a material and ambient occlusion per surface voxel. `renderSprite` casts one isometric ray per pixel and lights the hit with a fixed key light, four-step ramps with cooler shadows (`rampLab` in `color.ts`), ordered dithering, gloss and metal highlights, see-through glass, a darker outline where the model meets the background, a line where a nearer part overlaps, and a two-step contact shadow. Props are snapped to a palette built from the room's tones; items keep their photo's colours. Prop faces stay in the SVG, invisible, so picking and dragging still follow the geometry. `renderView` draws the same grid from the photo's camera, for fitting.
- **Item models.** `Model` opens an editor for a detailed model of the remembered object: up to 12 parts in item space, where the footprint fills the unit square and the height can reach 6 units (`packages/domain/src/iso-item.ts`). Shapes are `lathe` (a side profile turned on an axis, with an optional open top, inner wall and liquid), `rbox`, `tube` (a Bézier), `extrude` and `blob`; the first shapes (`cylinder`, `box`, `cone`, `handle`, `lid`) still load and are drawn as the new ones. Parts carry a material and up to six paint layers (`band`, `stripes`, `dots`, `top`, and palette-indexed `decal`s at most 64 × 32). A part can be locked so a refit keeps it.
- **Fitting to the photo.** `POST /api/item/draft` (run kind `item`) cuts the sighting out of its stored photo with SAM's mask (`maskedCrop`; the demo rasterizes `desk.svg`), picks an archetype (`iso-archetypes.ts`: mug, cup, bottle, can, book, box, plant, lamp, device, generic) and runs `fitItem` (`item-fit.ts`). It clusters colours in OKLab and merges lit and shaded clusters of one material. It finds the axis from the narrowest rows and a handle from the rows that stick out on one side, and reads the camera's elevation from the surface pin's foreshortening or else from the rim's ellipse. It then corrects the side profile for the stacked-ellipse outline a lathe makes from above, finds bands down the front, and unwraps the visible half of the surface into a decal. Finally it renders the model from the camera and nudges its numbers by coordinate descent until the silhouette matches the mask (at most 48 renders). The result is stored with a fit record: archetype, numbers, IoU, ΔE, elevation, views, crop and assists. `sampled` makes no model call. `spark` adds Meta's models, each only able to help: Spark names the archetype and material (`itemClassSchema`); SAM segments parts inside the crop (a handle, the liquid), which the fitter uses instead of its own guesses; Spark then compares a render with the photo and suggests corrections clamped to ±20% (`applyCheck`), kept only if the silhouette still matches. A later sighting of the same object is fused into the shape (`fuseFits`). `POST /api/item/refit` fits again to the stored crop, keeping locked parts; `GET /api/item/crop` serves the crop for the editor's `Photo vs model` overlay. `POST /api/item/save` stores edits and scores them again against the crop. The model lives in desk memory as `item`, survives new sightings, and is cleared on reset with the object. Extra objects (below) get models the same way, by `objectId`. `bun scripts/fit-bench.ts` measures fit accuracy on synthetic crops, the demo and any real crops in `testdata/items/`.
- **Templates and custom scenes.** Every scene is built from the prop palette in `packages/domain/src/iso-templates.ts`: desks, tables, shelves, a fridge, lamps, books and so on. One placed template is a group. Its props and surfaces share the group id as a prefix (`desk`, `desk:leg-0`, surface `desk:top`), and it moves, turns and goes as one. The presets are made of these templates too. `Edit layout` (the room's inspector) starts from a preset, an empty floor or a Spark draft. You add templates (`addTemplate` finds the first spot where nothing overlaps), drag and turn groups, and remove them. Tabletop templates settle onto whatever surface ends up under them (`settleGroup`). Groups that cut into each other are flagged, since the depth sort assumes boxes don't intersect. `POST /api/scene/save` checks the scene against `isoSceneSchema` and keeps it in desk memory as `scene`, which reset keeps. It becomes the room in the outline, and its surfaces can be pinned like a preset's. Saving a scene that no longer has the pinned surface clears the pin.
- **Spark layouts.** `Draft with Spark` in the scene editor (`POST /api/scene/draft`, run kind `layout`) asks Spark only which templates stand where on a grid, checked against `sceneDraftSchema`. `buildScene` builds the geometry, puts floor things first, settles tabletop things onto their surfaces, and checks the result against `isoSceneSchema`. Nothing is saved until you save it. The demo answers with a fixed layout of the illustrated desk.
- **A scene from one photo.** `Upload a photo` in the scene editor (`POST /api/scene/from-photo`, run kind `photo`; `packages/domain/src/photo-scene.ts`, `apps/server/src/photo.ts`) drafts the whole scene and its objects in two billed calls, three with the check. Spark lists up to 16 things, each a template or an archetype with a role (`surface`, `furniture`, `object`), what it stands on and a loose box in thousandths (`photoInventorySchema`). It gives no sizes, tiles or turns. One SAM call takes every box as a prompt under its own id (`segmentBoxes`, `buildObjectPrompt`), so each mask comes back labelled, and is saved as an ordinary segment run that sightings can point at. `layoutPhoto` measures the rest. The biggest surface's mask has the things standing on it filled in and its legs opened away (`surfaceTop`). The biggest quad inside its hull is then nudged into place (`fitSurfaceQuad`), and an IoU under 0.85 leaves the pin to a person. The corners are refined again so that the whole template (top, front and legs), drawn from the camera they imply, matches the mask (`refinePin`). `cameraFromPin` recovers a pinhole camera from the corners. It measures the focal length from the right angle at the corners when the perspective shows it, and otherwise assumes a typical lens. The surface's depth follows from its width. Objects stand where the bottom of their mask meets the plane of what they're on. Furniture stands where its mask meets the floor, which is the surface's plane moved down by the template's height. Every thing is then drawn from the camera and scored against its mask, ignoring pixels another mask may hide. Placed templates are nudged by turns and fractions of a tile while the match improves (at most 40 tries each). The local fitter models each object from its own mask, with no model call. With the check, Spark sees the photo beside a flat drawing (`flatView`) and names what's missing or extra (`photoCheckSchema`). Anything missing gets one more SAM call if today's spending limit has room, and is kept only if the scene still matches. A draft whose worst-case cost today's spending limit can't cover is refused before any call. In review, the layout runs again in the browser on every change: a dragged pin corner, a thing drawn as another template, or one removed. `POST /api/scene/from-photo/save` writes the scene, the pin, the ticked objects (the first becomes the main one) and their models in one go. Untracked objects that have a template stand in the scene as props (`sceneForSave`). Without a surface, things are spread by where they are in the frame, and the pin is left to a person. The demo lists the illustrated desk's desk, mug, book and bottle, with masks drawn from the SVG's own shapes. `bun scripts/scene-bench.ts` measures pin, depth and position errors on synthetic photos.
- **More objects, zones and lights.** The outline adds up to four more objects and eight more zones (`others` and `rules` in desk memory). An extra object is confirmed by hand from a mask in the newest segmentation, of any concept, and then tracked only in segmentations of that same concept (`desk/objects/select`, `desk/objects/track`). A rule ties one object, one zone and one entity together (`entityId`, a light or a switch, optionally picked as a fixture by `fixtureId`; rules saved with only `lightId` are upgraded on load by `upgradeMemory`). `ruleGate` runs the same checks as `placementGate`: a fresh sighting, a zone drawn on that image or carried over by the fixed-camera assumption, and the whole box inside the zone. Each rule keeps its own inside/outside story, switches its light only on `entered`, and claims `segmentRunId:ruleId` before the call, so one segmentation can try each rule at most once. Rules are checked when their object is tracked (the mug's rules too, after the main zone) and on `Check rules`. The main zone, the main lamp and their tests are unchanged. Live lights are `HA_ENTITY_ID` plus `HA_EXTRA_ENTITY_IDS`, live switches are `HA_SWITCH_ENTITY_IDS`, and the control adapter (`control.ts`) refuses any other entity. It calls `light/turn_on`, `light/turn_off`, `switch/turn_on` or `switch/turn_off` by the entity's prefix, asks for brightness and warmth only when turning a light on, and polls until the entity reports the requested state. Demo mode has three virtual lights and two virtual switches (`DEMO_SWITCHES`). Only a light turned on counts as live proof of the lamp. In a scene, a lamp prop stands for the main light unless the scene editor ties it to another (`lightId`). The demo's synthetic SAM only knows the mug, so in demo mode rules can only target the mug.

- **Flat things and lamps.** A `device` (a mouse, a remote, a switch plate) is its own shape family, `flat`: one `extrude` part whose outline is read off the mask in twelve directions from its middle, as a reference photo from above shows it, with its top colour and any print as a top decal. A photo from above can't show height, so it comes from `knownHeight` (a fixture's usual size) or a typical one. The fitter's camera looks from the iso corner, which would see a top-down photo turned 45°, so a flat model is scored by drawing its outline flat over the crop (`scoreFromAbove`) rather than by rendering. A `lamp` is a turned body (base, stem, shade); a shade keeps widening below its rim, so a lamp's camera angle is read from its base's bottom edge instead. Rim angles are read only from rows up to the widest point. Lamps still miss the 0.9 IoU target (about 0.85: the thin stem is lost between profile samples) and are listed as a known gap in the fit bench.
- **Fixtures ([plan](plans/fixtures.md)).** Things placed in a room by hand, which the camera can follow once confirmed in its view ([watching](#tracking)): a lamp, a wall switch, a mouse (`packages/domain/src/fixture.ts`). Each stands in one scene, on a surface or the floor, with a voxel model and a control: `none`, or a `light` or `switch` entity. They live in desk memory as `fixtures`, survive reset, and settle when the person's own scene changes (`settleFixtures`: a lost surface drops them to the floor; dropping the scene drops its fixtures). `POST /api/fixtures/save` checks where one stands (`fixtureProblem`) and that its entity is configured; `POST /api/fixtures/delete` unlinks rules that picked it; `POST /api/fixtures/control` turns its light or switch on or off as a `lamp` run. Any confirmed action on an entity, from a rule too, sets `state` on the fixtures that switch it (`noteControl`); an unconfirmed one clears it. `POST /api/fixtures/draft` (run kind `fixture`) drafts one from a reference picture: the thing's mask is cut out (`maskedCrop`) and modelled by `draftModel` in `item.ts`, the same part masks, fitter and Spark check that `POST /api/item/draft` uses, then sized for the scene it's meant for (`sizeInTiles`: a desk is 120 cm wide, else a tile is 25 cm). Nothing is saved; the draft (`FixtureDraft`) carries the model, a suggested control, the size and the reference photo. Saving a fixture whose reference is a draft keeps the draft's swatches and fit record, rescored against its crop. Live, the person's photo is checked and re-encoded (`validateImage`), Spark names the one thing in it (`fixtureClassSchema`: a label, an archetype, a material, a suggested control, a loose box in thousandths and its usual size in cm; an optional name from the person is passed along), and one SAM call outlines it from that box (`segmentBoxes`); the biggest outline wins, and none is a 422 that asks for one thing filling the frame. The crop then goes through `draftModel` with part masks and Spark's check. Up to five billed calls; a draft whose worst case today's spending limit can't cover is refused before any call, and the run is billed by its Spark tokens like `item`. Demo mode drafts only from the bundled `mouse.svg` and `lamp.svg`, whose masks are the SVGs' own `<name>-body` polygons. In the lab, fixtures have their own section in the outline. `Add fixture` opens photo first: the drop zone for a photo of the thing (`Take a photo` opens the camera on phones, `Upload` a file picker; the photo is scaled to 1280 px in the browser, and an optional name tells Spark what it is), and in demo mode the bundled pictures instead. The review shows the reference beside the model, then the name, `Light · Switch · Just a thing` (preselected from the suggestion, and only offering kinds with configured entities) and the room. `Place it` switches the canvas to that scene, where a ghost of the model follows the pointer onto the highest surface under it, or the floor, until a click saves it (`GET /api/fixtures/reference` serves the photo for review). A selected fixture can be switched on and off, moved the same way, turned, changed or deleted (`FixturePanel.tsx`). In the room a light that is on glows like a lamp; a switch shows its state in its label, never in amber. A fixture can also be drafted from a box drawn on the desk photo (live: Spark sees only the boxed part, SAM outlines it from the box; demo: the box picks one of the illustrated desk's own outlines), and its model edited in the item editor like an object's. Lamps that are part of a room's layout are listed under Fixtures too and can be switched by their entity; every lamp glows by its light's newest confirmed state, from a switch, a rule or the mug's zone.

Amber stays reserved for lamps: an iso lamp warms only once an action on its light is confirmed.

## Home Assistant entities

([plan](plans/mqtt.md)) Rules act _on_ Home Assistant over REST. In the other direction, Living Layer publishes entities of its own over MQTT discovery, which appear in Home Assistant under one _Living Layer_ device, for automations and dashboards there. Nothing is published until someone adds one in the lab's outline (_Home Assistant_ section).

- **What one is.** `exposed` in desk memory (`packages/domain/src/expose.ts`): a name, a key, a kind (`binary_sensor` or `sensor`) and a source. The key `office_presence` gives `binary_sensor.ll_office_presence`; Home Assistant ids have one dot, so the `ll_` prefix stands for the namespace. Sources: `in_zone` (a zone's SAM verdict), `any_inside` (any of several zones; as a sensor, how many), `zone_of` (which of an object's zones it's in, an `enum` sensor), `status` (seen, searching or missing, from the watcher, else desk memory), `motion` (pixels changing in a zone, held for `holdS`; the watcher's stillness rule per zone, no SAM, needs the watcher on and the camera fixed) and `watching`. Zones are named by rule id, the main zone as `main`. Reset keeps entities; one whose zone or object is gone shows as unavailable, so automations notice.
- **Zones that only tell Home Assistant.** A rule's entity may be null (_nothing: tell Home Assistant only_). `ruleGate` decides it like any other, it keeps its inside/outside story, and it never claims or switches anything. A rule panel's _Also show in Home Assistant_ makes an `in_zone` entity for it.
- **States.** `evaluateExposed` is the only place states are worked out, from desk memory and the watcher's `exposeWatch()`. Zone sources read SAM verdicts only, like the lamp. While the watcher runs a verdict stands until SAM changes it; without it the last verdict stays, with `stale: true` among the attributes. A zone with no verdict yet is unavailable.
- **Publishing.** One `Exposer` per mode (`apps/server/src/expose.ts`) syncs after every successful POST to the desk, fixture, scene, item, watch and expose routes, on every watcher update, and every 5 s for motion holds. It diffs `exposeMessages` (configs first, all retained) against what it last sent, publishes the changes, and clears what went away; an entity that is only unavailable keeps its last state. Config topics are remembered in `settings`, so ones deleted while the server was down are cleared on the next sync. Each config carries `unique_id` (`livinglayer_<install id>_<entity id>`, the install id made once in `settings`), `default_entity_id` (not the removed `object_id`), and two availability topics, `<base>/status` (the broker's last will) and the entity's own. `MqttLink` resends everything on each connect and when Home Assistant publishes `online` on `<prefix>/status`. Live only: demo mode never touches the network and keeps a log of what it would have sent, which the entity panels show (_What it would publish_). The lab follows states through `GET /api/expose/:mode/events`. Broker credentials stay in `.env`; the lab sees the broker's state and a generic note.

- **Presence, locally.** An `occupied` source compares a zone with how it looked empty, which the person shows once (_It's empty now: learn it_, `POST /api/expose/learn-empty`), so someone sitting still still counts. With the feature model (`bun run fetch-model`) the zone's patches are compared (`featureDifference`: the share whose cosine with the empty look is under 0.8); without it, a 32 × 24 grey sample (`pixelDifference`), which light changes fool. Occupied from 12% changed, clear again under 6%, every 3 s while watching (every frame in the demo), from the watcher's grey frames, so no extra ffmpeg run (`packages/domain/src/occupancy.ts`). Empty looks are kept in `settings` per mode and zone. Nothing paid by default: `samConfirm`, a per-entity opt-in the form marks as billed, asks SAM for `person` once each time the zone starts to look occupied (at most once a minute), and the entity is on only if a person's box overlaps the zone. The thresholds are first guesses, not tuned on real rooms.
- **More kinds.** A `device_tracker` follows an object: its zone's name, `home` when it's in none, `not_home` when missing. An `event` entity (`event_types: entered, left`) gets each zone decision that entered or left once, not retained (`zoneEvent`; a new entity starts from what is already decided). A `switch` (`watching`) turns watching on and off with the camera last chosen in the lab (`setWatching`, shared with `POST /api/watch`); a `button` (`check_rules`) runs `verifyRules`. Commands arrive on `<base>/<key>/set` and `/press` and are taken only for our own switches and buttons, with their exact payloads (`commandOf`); the lab lists the last ten and what came of them. Live only.
- **Lights over MQTT.** `MQTT_DEVICES` names lights and switches by the topic they report on. They join the entities rules and fixtures may switch; with no `HA_ENTITY_ID`, the first such light is the main lamp. `MqttControl` publishes `{"state":"ON"}` (with brightness 217 of 254 for a light turned on) on `<topic>/set`, not retained, and waits up to 3 s for the device's JSON report with that state. Its `LampResult` reads the same as Home Assistant's: confirmed means the device reported it, not that light was seen. A retained report already in that state confirms at once.

## Lamp results

Home Assistant accepting a request, the entity reporting the requested state, and the bulb actually lighting up are three separate things. `LampResult` records the first two (`accepted`, `stateConfirmed`). `physicalEffectVerified` is always `false`, because the software has no way to see the lamp.

## Not built yet

- Recognising the same mug by appearance when SAM answers. SAM's answer is matched to the last sighting by position (`pickTracked`), so two mugs swapping places would still fool it; the feature model only finds a lost thing again.
- Watching a phone camera on the server: a phone streams to the tab, peer to peer, and the server never sees its frames.
- Camera calibration, so a zone can carry over between frames from a camera that did move
- Combined conditions, such as two objects in their zones before one light turns on. Each rule is one object, one zone and one light. Entities shown in Home Assistant let its automations combine them instead.
- Extra objects in demo mode: the synthetic SAM output only has the mug
